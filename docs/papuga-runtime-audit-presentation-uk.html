Сильна кореляція

Hidden proposal — найсильніший кандидат

1. Показ Coordinator монтує AutoFixProposalView у NSHostingView.
→
2. Приховування hide() викликає лише orderOut; contentView залишається.
→
3. Сильна runtime-кореляція repeatForever і retained view узгоджуються з ViewGraph, layout та shadow work.
Поточний стан
  • панель прихована, view змонтований;
  • анімація не прив’язана до visibility;
  • heap зберігає AutoFixProposalView.
→
Мінімальне виправлення
  • очистити hosting content після hide;
  • перемонтовувати view на show;
  • врахувати Reduce Motion.
Критерій: CPU та wakeups повертаються до baseline ≤ 2 с після dismiss.

Memory footprint

Великий reachable footprint, не класичний leak

747.8 MB physical footprint
795.6 MB peak footprint
519.1 MB live malloc zones
23.8 KB unreachable за leaks

Що показало коротке спостереження

  • 5,197,725 live allocations;
  • через кілька хвилин лише +11 nodes;
  • немає доказу активного росту heap.

SymSpell: сильний висновок за формою типів

До ~129.4 MiB generic String/Array/Dictionary shape узгоджується з двома eager delete indexes. Без allocation stacks або before/after build це не точна атрибуція.

Оптимізувати після вимірювання. Спочатку lazy-load exact build; compact word IDs — лише якщо внесок підтвердиться.

Найвищий пріоритет

Три trust-boundary ризики

Підтверджено

Raw text у Unified Logs

Оригінали, кандидати й dictionary words інтерполюються з privacy: .public.

Підтверджено

Секрети в clipboard history

ConcealedType і TransientType не перевіряються до читання та JSONL persistence.

Ймовірно

OpenCode без Papuga deny policy

Ефективні tool permissions залежать від installed version і user config; runtime canary ще не виконаний.

Зараз
  • user text виходить за локальні retention controls;
  • password-manager content може потрапити на диск;
  • AI classification може успадкувати permissive tools.
→
Потрібний контракт
  • private-by-default structured logs;
  • skip confidential items до читання bytes;
  • versioned deny-all policy + side-effect canary.

Підтверджена втрата даних

5,000 записів у RAM можуть стерти старіші записи на диску

Disk history Файл може містити більше 5,000 записів.
→
Memory snapshot Store зберігає лише capped window до 5,000.
→
Full rewrite Status update або filtered clear перезаписує файл із capped snapshot.
>5,000 старіші записи можуть бути видалені без попередження
2 history stores мають споріднений rewrite-ризик
1 shared invariant: mutation не втрачає unseen rows
Regression seam: fixture із понад 5,000 rows → update / filtered clear → усі untouched IDs залишаються.

Clipboard transaction

Одна глобальна pasteboard, кілька конкурентних власників

Підтверджені дефекти

  • copyOnly відновлює старий clipboard і ламає власну семантику;
  • deferred restore перезаписує новішу копію користувача;
  • overlapping switch tasks змішують copy, paste та restore;
  • retry завершується, коли changeCount уже змінився, а flavor ще nil.

Мінімальний контракт

  • одна серіалізована switch transaction;
  • restore лише якщо Papuga досі володіє clipboard;
  • copyOnly залишає converted text у pasteboard;
  • читання повторюється до deadline, а не першого changeCount.
Небезпечна послідовність

Papuga copy → user copy → delayed restore

→
Правильна послідовність

snapshot owner → operation → compare owner → restore або skip

09 / 12

Concurrency та lifecycle

Start, cancel і finish не утворюють один контракт

Event tap

Success повертається до CGEvent.tapCreate. Швидкий start/stop може залишити ghost tap або створити дублікат.

AI sheet

Provider та apply tasks переживають dismissal і можуть продовжити mutations після закриття UI.

CLI process

Після SIGTERM процес може не завершитись, а Papuga — polling кожні 10 ms без верхньої межі.

Інші correctness gaps

  • layout corroborator не будує CharacterMapper maps;
  • TISSelectInputSource failure звітується як success;
  • onboarding тримає view graph і завершується двічі.

Один lifecycle invariant

Після stop/dismiss жодна task, thread, process або UI mutation не продовжує роботу.

10 / 12

Після correctness

Оптимізації з вимірюваним результатом

MainActor і hot paths
  • candidate generation реально винести з MainActor;
  • прибрати raw notice logging на кожне keyDown;
  • вимкнути зайвий flagsChanged dispatch.
Disk I/O
  • coalesce decision aggregates замість rewrite/word;
  • batch AI apply замість N повних store mutations;
  • threshold pruning у довгих app sessions.
Bounded memory
  • byte cap для clipboard representations;
  • lifecycle bound для prediction caches;
  • streaming limit для Ollama response.
SymSpell
  • спочатку lazy-load і allocation stacks;
  • компактні postings лише після підтвердження;
  • окремо виміряти latency першого query.
Порядок важливий: correctness → lifecycle → performance. Інакше оптимізація просто зробить неправильну поведінку швидшою.

Рекомендований порядок

Чотири вертикальні зрізи

01 · Межа довіри

Захистити дані

Private logs, concealed clipboard, versioned deny-all policy. Перевірити sentinel і side-effect canary.

Зупинити offscreen CPU

Unmount proposal після hide та окремо переміряти CPU, wakeups і footprint на exact build.

03 · Цілісність даних + життєвий цикл

Прибрати втрати й races

>5,000-row tests, serial clipboard transaction, потім join event tap і cancel AI/process/apply.

04 · Продуктивність

Оптимізувати виміряне

Background prediction, coalesced writes, bounded payloads, lazy-load SymSpell із before/after вимірюванням.
